**What is live.** The production vendor is `~nisfeb` at `https://urbit.nisfeb.com`, running armillary version 11 in live mode. Verified today end to end with real money and a real model: a $5 card purchase credited by webhook, a lease minted on OpenRouter with a cap of the balance divided by 1.3, one Haiku completion billed at 39 microdollars for a 30 microdollar upstream cost, the lease dropped and the key deleted upstream. What the vendor answers a customer ship, and where it differs from what the branch was built against:

- `GET /api/plans` lists exactly three top-up plans, `topup-5`, `topup-10`, `topup-50`, price equal to credit, and no subscription plan. The Subscribe button must therefore be absent on the card; the branch hides it when no subscription plan exists, confirm that on the live check. `min_topup` is 5,000,000.
- The mode is lease. `GET /api/inference` answers `mode` `lease`, `base_url` `https://openrouter.ai/api/v1`, an OpenRouter runtime key scoped to that ship, and `models` naming thirteen OpenRouter model ids (`anthropic/claude-haiku-4.5`, `anthropic/claude-sonnet-4.5`, `openai/gpt-5`, `google/gemini-2.5-flash` and so on). The model picker offers those ids, nothing else; the key can reach any OpenRouter model, but the catalog is the product.
- In lease mode the balance moves only when the vendor reconciles, every ten minutes. A request does not lower the balance on the card at once. The history row for a lease charge carries `mode` `lease` and `cost`, no model and no token counts, so the second line of a charge is absent there. Say nothing about the lag on the card beyond the existing Refresh.
- Out of credit in lease mode comes from OpenRouter, not the vendor: an HTTP 402 with OpenRouter's own error body once the key's limit is spent. `AiClient` already turns any 402 into `outOfCredit`, so the Top up action reaches the card either way; keep it that way when resolving conflicts.
- Stripe Checkout runs under Managed Payments, Stripe as merchant of record, so tax is added on the Stripe page and the charge can exceed the button's figure. The credit is the button's figure. One line under the sizes: "Tax may be added at checkout." The line item on the Stripe page reads "Talon inference credit".
- Bitcoin is a BTCPay invoice on mainnet with a sixty-minute window; it settles after one confirmation. The BTCPay node was still syncing today, so the bitcoin rail is not part of this live check; the code path stays as built.
- The desk on a customer's ship comes from `~ricsul-bilwyt`, not yet published there. The one real ship with armillary installed today is `~nisfeb` itself, and a ship is a valid vendor for its own account, which is how the live check runs.

## 2. A capability flag for the purchase flows

The App Store may not allow buying credit through an outside checkout from an iOS app. Put the sheet, the Top up and Subscribe buttons and the Top up action on the 402 surfaces behind `expect val isArmillaryPurchaseSupported: Boolean` in `ui/Capabilities.kt`, `true` on every platform today. The card without purchases still shows the balance, the warning, the history and the vendor; the low-balance line then reads "Top up from another device." This is the same flag pattern as `isDailyDigestSupported`, added now so that switching iOS off later is a one-line change rather than a rebuild.
