# Armillary Phase 5: leases and the report

**Goal:** the path for clients we own. A customer ship asks for a lease over ames and gets a real OpenRouter key capped at its balance; Talon calls OpenRouter directly with it; the vendor reconciles what was spent every ten minutes from OpenRouter's own usage figure, tracks the cap to the balance, disables the key at zero and re-enables it on credit. `GET /api/inference` on the customer ship answers lease mode when a lease is held. The tick fiber also expires stale checkout rows and compacts old ledger rows, and the vendor page gains the Report view. Built on phase 4's head. Spec sections 5 (Lease), 6 (the lease ops), 8, 9 and 10 (`tick.sig`, `lease.json`) are the requirements; every earlier brief's rules and recipes hold. ## OpenRouter facts, checked 2026-09-19 and 2026-09-20 against its docs

- Every management call is under `https://openrouter.ai/api/v1/keys` with `Authorization: Bearer <provisioning key>`.
- `POST /keys` with `{"name": "<name>", "limit": <USD number>}` (optional `limit_reset`, `include_byok_in_limit`, `expires_at`) answers 201 `{"key": "sk-or-v1-...", "data": {"hash", "name", "label", "limit", "limit_remaining", "limit_reset", "disabled", "usage", "usage_daily", "usage_weekly", "usage_monthly", "created_at", "updated_at", ...}}`. The plaintext `key` is returned only here.
- `GET /keys/<hash>` answers `{"data": {...the same fields...}}`; `usage` is credits spent in USD, a decimal number.
- `PATCH /keys/<hash>` takes any of `name`, `limit`, `disabled`, `limit_reset`, `include_byok_in_limit`. `DELETE /keys/<hash>` removes it.
- A key with `disabled: true`, or whose usage has reached its `limit`, is refused by the inference API.

## 1. The pure lib

`code/lib/armillary-openrouter.hoon`, import-free, its own JSON getters and decimal helpers like the other provider libs. `+usd-of |=(micro=@ud @t)`: microdollars to a decimal string with six places (`1.500.000` is `1.500000`). `+micro-of |=(j=json (unit @ud))`: a JSON number (OpenRouter sends numbers, not strings; `%n` carries the digits as text) to microdollars at scale 6, truncating beyond six places. `+create-request |=([key=@t name=@t limit-micro=@ud] request:http)`: POST `/keys` with `name` and `limit` (as a JSON number, rendered from `usd-of`). `+read-created |=(body=@t (unit [key=@t hash=@t usage=@ud limit=@ud disabled=?]))`. `+get-request |=([key=@t hash=@t] request:http)`. `+read-key |=(body=@t (unit [hash=@t usage=@ud limit=@ud disabled=?]))`. `+patch-request |=([key=@t hash=@t limit=(unit @ud) disabled=(unit ?)] request:http)`: PATCH with only the fields given. `+delete-request |=([key=@t hash=@t] request:http)`. `+debit-for |=([usage=@ud seen=@ud pct=@ud] @ud)`: `ceil((usage - seen) * pct / 100)`, 0 when usage is not above seen. `+limit-for |=([usage=@ud balance=@sd pct=@ud] @ud)`: `usage + floor(balance * 100 / pct)` when the balance is positive, else `usage` (a cap at what is already spent disables spending as surely as `disabled`, but `disabled` is set too). Tests in `tests/lib/armillary-openrouter.hoon`: `usd-of` on three cases; `micro-of` on `0.0123` (12.300), `1` (1.000.000), `0.00000049` (0), a string (`~`); the create request's method, URL, auth header and body; `read-created` on a fixture (the key and the hash come back; `usage` 0); `read-key` on a fixture with `usage: 0.75` and on junk; `patch-request` with only `disabled`, with only `limit`, with both (body keys); `debit-for` when usage moved, when it did not, and rounding up; `limit-for` with a positive and a negative balance. About 14 arms.

## 2. Lease state and the vendor ops

`/accounts/<ship>/lease.json` holds `{provider, hash, key, usage_seen, limit, disabled, made, checked}` (`key` is the OpenRouter plaintext key; it is a secret: never in the ring, never on an owner read route except as `hash` and the figures, never in a view other than that ship's own). `+$ lease`, `en-lease` (full, for storage and the ship's own view), `en-lease-owner` (no `key`), `de-lease`. Settings gain `lease_provider` (the provider id whose provisioning key mints leases, blank means no leases; the page offers the OpenRouter providers). Writer ops `set-lease` (the whole row), `drop-lease` (delete the file), `touch-lease` (`usage_seen`, `limit`, `disabled`, `checked`).

`+reconcile |=(who=@p (fiber ,[ok=? why=@t]))`, the one arm every path uses. Read the lease; none is ok `no lease`. Read the provider named by `lease_provider`; `+fetch` the get request; on a non-2xx answer `[| 'openrouter answered <status>']` and leave the row alone. `read-key`; when `usage` is above `usage_seen`, poke `debit` with `amount` `debit-for`, `cost` `usage - usage_seen`, `model` `openrouter`, `mode` `lease`, `ref` `lease-<unix seconds>`; then compute the balance after the debit yourself (the balance read before the poke minus the debit) rather than reading it back, since the writer may not have applied the poke yet. Then the cap: `want-limit` is `limit-for`, `want-disabled` is the balance at or below zero; when either differs from the row, `+fetch` the patch request; on a 2xx `touch-lease` with the new figures and `checked` now; on failure `touch-lease` with `usage_seen` and `checked` only, answering `[| ...]`. A closed account's reconcile deletes the key upstream and drops the lease.

The inbox ops: `lease`: when `lease_provider` is blank, note `not offered` and rewrite the view (the customer's route reads that as 404 `no lease for this account`); when the account has no lease, `+fetch` the create request with `name` `armillary/<ship>` and `limit-for` from the current balance and usage 0; on a 2xx `read-created`, `set-lease`, then `write-view`; on failure note `openrouter answered <status>` and set a `lease_error` on the view (a field the view gains, blank when fine); when a lease exists, `reconcile` then `write-view`. `drop-lease`: `+fetch` the delete request (a 404 counts as gone), `drop-lease`, `write-view`. Both from the inbox fiber, with the existing ceiling comment. `close-account` (the writer) cannot fetch, so the owner's `POST /api/accounts/<ship>/close` route deletes the upstream key first through the same delete request and then pokes `close-account`; the gate's hard delete does the same.

The view's `lease` is `{"provider": "openrouter", "base_url": <the provider's base_url>, "key": <plaintext>, "hash", "limit": <microdollars>, "usage": <microdollars>, "disabled": <bool>, "models": [<catalog ids on that provider>]}` or `null`, and the view gains `lease_error`. The owner's account detail shows `en-lease-owner` plus a Reconcile now button (`POST /api/accounts/<ship>/reconcile`, owner, answers the reconcile's outcome) and a Drop lease button (the delete request then `drop-lease`).

## 3. The tick

`/tick.sig`, a long-lived fiber like `client.sig`: `rise-wait`, then loop: `tick-pass`, `set-timer` ten minutes, `take-poke-from` (a prod or the timer), `cancel-timer`, recurse by arm name. `tick-pass`: for every account (walk `/accounts`), `reconcile` when a lease exists and `checked` is older than nine minutes; mark every checkout row whose `expires` has passed and whose status is `pending` or `processing` as `expired` (a `set-checkout` per row, or one `expire-checkouts` op that does the walk in the writer: prefer the writer op); compact: for every account, ledger rows older than 90 days are folded into one row per month per kind through a `compact` writer op that writes the summary row (kind, the summed `amount` and `cost`, `ref` `compact-<yyyy-mm>-<kind>`, `note` `<n> rows`, `at` the month's first second) and deletes the originals, then refolds the balance; a summary row is itself older than 90 days and is skipped by the `ref` prefix. Add `[%fall %& [/ %'tick.sig'] [[/ %sig] ~]]` to `on-load`. The owner's `POST /api/tick` prods it (owner only; the gate uses it instead of waiting ten minutes).

## 4. The customer side and Talon's route

`POST /api/lease` on the customer ship: queue `lease`, prod the client, wait up to 30 seconds for the view's `lease` to be non-null or `lease_error` to be set, answer the lease (the ship's own view carries the key; the route answers it, since the caller is the ship's owner or Talon over the owner's cookie) or 404 `no lease for this account` when the view says `not offered`, or 502 with `lease_error`. `DELETE /api/lease`: queue `drop-lease`, `store-lease` cleared at once, answer ok. `store-lease` (existing op) keeps the view's lease object in `/lease.json` on every `absorb-view`, so `GET /api/inference` answers `{"mode": "lease", "base_url", "key", "models"}` when `/lease.json` holds a key and the view's `disabled` is false, else the proxy config from phase 2. A disabled lease (balance gone) falls back to the proxy, which answers 402 with a clear message, so the client's one code path still works. The customer's Keys view gains a Lease card: Take a lease, the lease's figures (limit, usage, disabled) and Drop; the inference config box reflects the mode.

## 5. The report

`GET /api/report?days=30`, owner: over every account's ledger rows with `at` inside the window: `credits` by rail (`{stripe, btcpay, owner, stub}` in microdollars), `charged` (debits' `amount`), `cost` (debits' `cost`), `margin` (`charged - cost`), `refunds`, `requests` (debit rows with mode `proxy`), `tokens_in`, `tokens_out`, `lease_spend` (debits with mode `lease`), `accounts` (with any row in the window), and `top_models` (the ten models by `charged`, each with `charged`, `cost`, `requests`). Summary rows count by their kind and amounts and carry no model. The page's **Report** view: the window chooser (7, 30, 90 days), the figures in a table in dollars, the top models table. No charts.

## 6. The stub, the gates, the docs, version 6

`scripts/fake-provider.py` gains the provisioning routes under `/api/v1/keys` (the lib takes `base=@t` in every request; the nexus derives it from the provider's `base_url` by stripping a trailing `/v1` and appending `/api/v1/keys`, so `https://openrouter.ai/api/v1` gives `https://openrouter.ai/api/v1/keys` and the stub's `http://127.0.0.1:3399/v1` gives `http://127.0.0.1:3399/api/v1/keys`; a unit test covers both). The stub requires `Authorization: Bearer <provisioning key>` (any non-empty value) on those routes, keeps an in-memory map by hash, answers create with a fresh key `sk-or-stub-<n>` and hash `h<n>`, `GET` with the record, `PATCH` updating `limit` and `disabled`, `DELETE` removing it, and `POST /stub/spend/<hash>` with `{"usd": <number>}` adds to that key's `usage` (the gate's way of simulating spend). The stub's chat route also accepts a leased key as the bearer, refusing 401 when the key is disabled or `usage` has reached `limit`, and adds the request's cost (`0.01` USD flat) to that key's usage, so a leased completion against the stub spends like the real thing.

`api-matrix.py`: `lease_provider` in settings round-trips; the report on an empty ship answers zeros and the shape; `POST /api/tick` answers ok. `ship-matrix.py`, both shapes, after the money steps: set `lease_provider` to the stub provider; `POST /api/lease` on the customer answers a key and `GET /api/inference` says `lease` with `base_url` the stub's; a completion against the stub with that key is 200; `POST /stub/spend` 0.10 USD, `POST /api/tick` on the vendor, then `?fresh=1` shows a debit of `130.000` microdollars (`0.10 * 130%`), the lease's `usage` 100.000 and the limit tracking `usage + balance/1.3`; the owner's detail shows the hash and never the key; spend past the balance, tick, the view says `disabled`, `GET /api/inference` says `proxy`, the stub refuses the leased key 401; a credit through the stub pay page, tick, the lease re-enabled with a higher limit; `DELETE /api/lease` and the stub no longer has the hash; a `lease` with `lease_provider` blank answers 404; the report shows the lease spend, the proxy request, the credits by rail and one top model; an expired checkout row: settings gain `checkout_minutes` (default 1440 for Stripe and 60 for BTCPay, one field each: `stripe_minutes`, `btcpay_minutes`); the gate sets one to 0, makes a checkout, ticks, and sees the row `expired`. Compaction is unit-tested on the fold (a fixture of rows across three months folds to the right summaries) and smoke-tested by the gate on a ship with no old rows (nothing changes). `live-matrix.py` gains the lease half: `OPENROUTER_PROVISIONING_KEY` from the environment, a real lease with a one dollar balance, one real completion through OpenRouter with the leased key against `openrouter/auto` or the cheapest catalog row, a tick, the debit printed, then drop. `docs/leases.md`: what a lease is, the cap rule, the reconcile cadence, what the client does (`GET /api/inference` and the fallback), what the owner supplies (a provisioning key on the OpenRouter provider row), the two things a lease cannot do (limit models, stream through the ship).
